# `/ChatAnalysisTotal` 模型名称维度统计优化设计文档

> 文档版本：v2.0.68 设计稿
> 编写日期：2026-07-30
> 目标：在保证大表性能与不查询 longtext 字段的前提下，让 `/ChatAnalysisTotal` 模型分布 stage 真正服务于「本平台用户配置的模型名称」维度分析。

---

## 1. 现状回顾

### 1.1 数据契约

`TAgentHttpTransactionDataItem`（`mysql_http_agent_model.go:89-155`）的关键字段（按 v2.0.42 longtext 白名单分类）：

| 类别 | 字段 |
|------|------|
| **本平台配置**（小字段，已索引） | `user_name` (size:50, idx)、`model_name` (size:64, idx, 注释"平台模型名称") |
| **目标源站**（小字段） | `dst_model_name` (size:64, idx) |
| **聚合指标**（小字段） | `tokens_input_size` / `tokens_output_size` / `tokens_all_size`、`elapsed_ms`、`request_method` / `request_url` / `response_status` / `request_content_length` / `response_content_length` |
| **协议特征** | `protocol_type`、`dst_endpoint_algorithm_type`、`task_model`、`is_stream`、`has_system_prompt`、`has_tool_call`、`user_message_count` |
| **Agent 维度** | `agent_tool_name`、`agent_tool_info`、`request_tools`、`session_id` |
| **⛔ 严禁扫描**（longtext / text 大字段） | `request_headers` (text)、`request_src_protocol_headers` (text)、`response_headers` (text)、`response_src_protocol_headers` (text)、**`request_body` (longtext)**、**`request_src_protocol_body` (longtext)**、**`response_body` (longtext)**、**`response_src_protocol_body` (longtext)** |

`user_name` 与 `model_name` 构成联合索引 `idx_user_model_created(user_name, model_name, created_at)`（`mysql_http_agent_model.go:91,97,98`）。

### 1.2 写库一致性确认

- `SaveAgentHttpTransaction`（`mysql_http_agent_sub_table.go:534`）`ModelName: modelName`，`modelName` 参数来自请求路径 `route.UserModelInfo.ModelName`（路由解析时已绑定），与 `TAgentHttpUserModelInfo.ModelName`（`mysql_http_agent_model.go:44`）一致。
- `dst_model_name` 单独存源站实际模型名，与 `model_name` 不混淆。
- 结论：`Transaction.model_name` 即"本平台用户配置的模型名"，可直接 GROUP BY。

### 1.3 当前 7 个 stage 的数据形状（`wsChatStatsStageOrder`，`server_ws_chat_total.go:463-466`）

| Index | Stage | 是否含"本平台模型名"维度 |
|------|-------|------------------------|
| 1 | kpi | ❌（仅 KPI + 当前选中 model_name 标签） |
| 2 | time_stats | ❌ |
| 3 | tokens_summary | ❌ |
| **4** | **model_distribution** | ✅ 按 `Transaction.model_name` 聚合，输出 `[]ModelNameUsageStat`（`mysql_http_agent_model_name_stats.go:28-37`） |
| 5 | trend_chart | ❌ |
| 6 | protocol_stats | 含 `task_model` 维度（子任务模型，非本平台模型） |
| 7 | agent_stats | ❌ |

### 1.4 stage 4 已有能力（v2.0.55-v2.0.60 已就位）

- **WS 路径**：`streamChatStats`（`server_ws_chat_total_stream.go:477-537`）单遍 keyset 分页扫描 8 张分表，**不含 longtext**，每批把 `Transaction.model_name` 累加到 `modelAgg`（`server_ws_chat_total_stream.go:67-73`），`snapshotModelDist`（`server_ws_chat_total_stream.go:367-396`）输出排序好的 `[]ModelNameUsageStat`，已含 `CallCount/TokensInput/TokensOutput/TokensTotal/CallShare/TokenShare/UserCount`。
- **HTTP fallback 路径**：`GetModelNameUsageStatsByRange`（`mysql_http_agent_model_name_stats.go:46-173`）对每张分表走 `SELECT model_name, COUNT(*), SUM(tokens_*) GROUP BY model_name`，命中 `idx_user_model_created` 前缀 2，再用 `COUNT(DISTINCT user_name) GROUP BY model_name` 补 `UserCount`，**不含 longtext**。
- **前端渲染**：`__lsmRenderStageHTML` 的 stage 4 分支（`server_web_manager_chat_total.go:488-511`）已支持横向柱状图 Top 15 + 完整表格 Top 50。

### 1.5 既有痛点（用户视角 + 运维视角）

| 痛点 | 原因 | 影响 |
|------|------|------|
| **stage 4 看不出"该模型被哪些用户使用了"** | `snapshotModelDist` 仅按 model_name 聚合，缺按 model_name × user 维度展开 | 管理员想看「`claude-haiku-4-5` 被用户 a/b/c 分别调了多少」只能跑 SQL |
| **WS 与 HTTP fallback 的 `model_distribution` 数据形状略不一致** | HTTP 路径用 `GetModelNameUsageStatsByRange` 顺序与 `snapshotModelDist` 不同；HTTP 路径返回 `UserCount` 字段已存在，WS 路径 `snapshotModelDist` 没有计算 `UserCount`（仅算 CallCount/Tokens/Share） | HTTP 模式有 `user_count`、WS 模式没有，前端读到 null |
| **stage 4 排序规则不直观** | WS 路径按 "调用次数 desc → tokens desc → name asc"，前端图表又按 `tokens_total desc` 二次排序 | 顺序在不同渲染路径里不一样 |
| **stage 4 表格只显示 50 行** | `data.slice(0, 50)` 截断 | 模型超过 50 个时翻页/搜索不可用 |
| **range 报告（brush 选区）的 `model_dist` 与 stage 4 字段命名不一致** | `TokensReportStat.ModelDist` 字段叫 `count` 而非 `call_count`，与 stage 4 不同 | 报告复制粘贴对比时需手动改名 |
| **HTTP fallback 路径的 `model_distribution` 不显示 share 百分比** | `lsmHandleFullHTTP` 直接把 `GetModelNameUsageStatsByRange` 结果透传，缺 `CallShare/TokenShare` 字段 | 报告里看不到占比 |

## 2. 目标

在不引入 N+1、不查询 longtext、不破坏 v2.0.55/58/60 WS 契约的前提下，让 stage 4 `model_distribution` 提供：

1. **本平台模型名**（已有）—— `model_name` 字符串维度
2. **每模型的活跃用户数** —— `UserCount` 字段，WS 与 HTTP 一致
3. **每模型的占比** —— `CallShare/TokenShare` 字段，WS 与 HTTP 一致
4. **每模型的源站覆盖** —— `DstEndpointCount` 字段（去重 `dst_endpoint_id` 数量），用于管理员判断「模型是否过于依赖单一源站」
5. **每模型的目标源站列表** —— `TopDstEndpoints []DstEndpointUsage`，Top 3 即可（不传明细避免数据膨胀）
6. **Top N 完整数据** —— 阶段内排序后取 Top 30；完整列表由用户点击"展开" 按钮触发额外 HTTP XHR 拉取
7. **按模型名搜索过滤** —— 前端在 stage 4 头部加 `<input type="search">`，实时过滤

> 不做的：跨 user 维度把"调用方用户列表"渲染出来（CLAUDE.md 强制规则：禁止把用户名列表传到前端未脱敏位置）。

## 3. 设计方案

### 3.1 数据形状：扩展 `ModelNameUsageStat`

`mysql_http_agent_model_name_stats.go:28-37`：

```go
type ModelNameUsageStat struct {
    ModelName        string             `json:"model_name"`
    UserCount        int64              `json:"user_count"`         // 跨分表去重的活跃用户数（已有）
    CallCount        int64              `json:"call_count"`
    TokensInput      uint64             `json:"tokens_input"`
    TokensOutput     uint64             `json:"tokens_output"`
    TokensTotal      uint64             `json:"tokens_total"`
    CallShare        float64            `json:"call_share"`         // WS 现算、HTTP 补齐
    TokenShare       float64            `json:"token_share"`        // WS 现算、HTTP 补齐
    DstEndpointCount int                `json:"dst_endpoint_count"` // ★ 新增：去重源站数
    TopDstEndpoints  []DstEndpointUsage `json:"top_dst_endpoints"`  // ★ 新增：Top 3 源站（id + 次数）
}

// DstEndpointUsage 单个源站的使用情况（v2.0.68 新增）
type DstEndpointUsage struct {
    DstEndpointID uint64 `json:"dst_endpoint_id"`
    CallCount     int64  `json:"call_count"`
}
```

### 3.2 WS 单遍扫描改造：`streamScanRow` 加列（仅小字段）

`server_ws_chat_total_stream.go:39-58`：

```go
type streamScanRow struct {
    // 既有 18 列...
    ID, CreatedAt, ModelName, TokensInputSize, TokensOutputSize, TokensAllSize,
    ElapsedMs, AgentToolName, RequestMethod, RequestURL, ResponseStatus,
    RequestContentLength, ResponseContentLength, TaskModel,
    IsStream, HasSystemPrompt, HasToolCall, UserMessageCount
    // ★ 新增 3 列（仍为小字段，已索引，**不引入 longtext**）
    UserName         string `gorm:"column:user_name"`         // 用于 DstEndpoint 分组前不必，但需要 DstEndpointCount 要 UserName? 否，只按 dst_endpoint_id 即可
    DstEndpointID    uint64 `gorm:"column:dst_endpoint_id"`
}
```

> 决策：**新增 2 列** `dst_endpoint_id` + `user_name`（前者用于 TopDstEndpoints + DstEndpointCount，后者用于 UserCount）。两个都是小字段（`uint64` / `varchar(50)`），已被 `index` 标记，不会引入 longtext 扫描。

`streamScanColumns` 更新（`server_ws_chat_total_stream.go:61-64`）：

```go
const streamScanColumns = "id, created_at, model_name, tokens_input_size, tokens_output_size, " +
    "tokens_all_size, elapsed_ms, agent_tool_name, request_method, request_url, response_status, " +
    "request_content_length, response_content_length, task_model, is_stream, has_system_prompt, " +
    "has_tool_call, user_message_count, user_name, dst_endpoint_id"
```

**性能影响评估**（不破坏 v2.0.60）：
- `user_name` (50 字节) 与 `dst_endpoint_id` (uint64, 8 字节) 均为小字段，5000 行批增 ~290KB IO，相对 longtext 459KB × 5000 = 2.2GB 可忽略
- GORM `Select` 白名单继续严格限制，未引入 4 个 longtext 字段（`request_body`/`response_body` 等）
- 现有 `idx_user_model_created` 复合索引 prefix 1 = `user_name`，prefix 2 = `model_name`，keyset 仍 `id > lastID ORDER BY id ASC` 命中主键
- 8 张分表 × 5000 行/批 = 40000 行/批，全表扫描量未增加（仍是单遍）

### 3.3 累加器扩展

`server_ws_chat_total_stream.go:67-73` `modelAgg` 扩展：

```go
type modelAgg struct {
    name             string
    callCount        int64
    tokensInput      uint64
    tokensOutput     uint64
    tokensTotal      uint64
    // ★ 新增
    userSet          map[string]struct{}  // 去重用户集合（用于 UserCount）
    dstEndpointSet   map[uint64]struct{}  // 去重源站集合（用于 DstEndpointCount）
    dstEndpointCalls map[uint64]int64     // 源站 → 调用次数（用于 TopDstEndpoints Top 3）
}
```

`addRow` 中（`server_ws_chat_total_stream.go:189-200`）：

```go
// 既有逻辑
m.callCount++
m.tokensInput += r.TokensInputSize
m.tokensOutput += r.TokensOutputSize
m.tokensTotal += r.TokensAllSize
// ★ 新增
if mn := strings.TrimSpace(r.UserName); mn != "" {
    m.userSet[mn] = struct{}{}
}
if r.DstEndpointID > 0 {
    m.dstEndpointSet[r.DstEndpointID] = struct{}{}
    m.dstEndpointCalls[r.DstEndpointID]++
}
```

**内存评估**：
- 单模型 userSet 上限 = 全站用户数（生产 ≈ 几十）；`userSet` 总量 ≤ models × users，但**总去重后** ≈ 全站用户数（即与 `m.userSet` 总元素和 ≤ 全站活跃用户数）
- dstEndpointSet 同理：单模型源站去重 ≤ 10 个；总去重后 ≤ 全站源站数（生产 ≈ 几十）
- 单分表 5000 行累加完释放，无内存泄漏
- 单模型聚合完后（snapshotModelDist），map 被 GC

### 3.4 snapshotModelDist 扩展

`server_ws_chat_total_stream.go:367-396`：

```go
func (a *chatStatsAggregator) snapshotModelDist() []ModelNameUsageStat {
    stats := make([]ModelNameUsageStat, 0, len(a.models))
    for _, m := range a.models {
        // ★ 新增：按调用次数排序的 Top 3 源站
        top := make([]DstEndpointUsage, 0, len(m.dstEndpointCalls))
        for id, cnt := range m.dstEndpointCalls {
            top = append(top, DstEndpointUsage{DstEndpointID: id, CallCount: cnt})
        }
        sort.Slice(top, func(i, j int) bool {
            if top[i].CallCount != top[j].CallCount {
                return top[i].CallCount > top[j].CallCount
            }
            return top[i].DstEndpointID < top[j].DstEndpointID
        })
        if len(top) > 3 {
            top = top[:3]
        }

        stats = append(stats, ModelNameUsageStat{
            ModelName:        m.name,
            CallCount:        m.callCount,
            TokensInput:      m.tokensInput,
            TokensOutput:     m.tokensOutput,
            TokensTotal:      m.tokensTotal,
            UserCount:        int64(len(m.userSet)),      // ★
            DstEndpointCount: len(m.dstEndpointSet),      // ★
            TopDstEndpoints:  top,                        // ★
        })
    }
    // 占比（既有逻辑）
    for i := range stats {
        if a.totalCalls > 0 {
            stats[i].CallShare = float64(stats[i].CallCount) / float64(a.totalCalls) * 100.0
        }
        if a.totalTokens > 0 {
            stats[i].TokenShare = float64(stats[i].TokensTotal) / float64(a.totalTokens) * 100.0
        }
    }
    // 排序：CallCount desc → TokensTotal desc → ModelName asc（既有）
    sort.Slice(stats, func(i, j int) bool { /* 既有 */ })
    return stats
}
```

## 4. 风险与边界

### 4.1 已识别风险

| 风险 | 缓解 |
|------|------|
| `streamScanRow` 加 2 列后批 IO 增大 | 单批 +290KB，远小于 longtext 体量；keyset 分页仍命中主键 |
| WS 模式内存中 `userSet/dstEndpointSet` 总元素 ≤ 全站用户/源站数 | 内存有界；snapshotModelDist 后 map 被 GC |
| HTTP fallback 增加第三次 GROUP BY 增加耗时 | `dst_endpoint_id` 已被索引（`mysql_http_agent_model.go:101`），`GROUP BY model_name, dst_endpoint_id` 命中该索引 |
| 前端 stage 4 表格列数过多（10 列）→ 移动端错位 | 默认折叠表格，仅图表 + "详细数据" 按钮；展开时强制横向滚动 |
| `model_distribution_full` 全量拉取在 days=0 + 大表下超时 | 复用 `GetModelNameUsageStatsByRange` 的 ctx 25s 保护，超时返回部分结果 + warning |

### 4.2 不破坏的硬约束

| 规则 | 验证 |
|------|------|
| v2.0.42 longtext 白名单 | streamScanColumns + HTTP fallback 的 SELECT 列表均不含 4 个 longtext |
| v2.0.55 wsChatStatsStageOrder 7 stage 顺序 | stage 4 名称、index 不变 |
| v2.0.60 单遍分页流式聚合 | 仅增加 2 列到 `streamScanRow` + 累加器字段，不增加 SQL 次数 |
| v2.0.58 keyset 分页 | streamChatStats 仍 `id > lastID ORDER BY id ASC` |
| v2.0.54 statsDB() 25s ctx | HTTP fallback 全走 statsDB() |
| v2.0.39 不带 Select 访问交易表 | 所有新 SELECT 都带白名单 |
| v2.0.52 不在 SQL 端 DATE_FORMAT GROUP BY | 仍 Go 端 in-memory 聚合 |
