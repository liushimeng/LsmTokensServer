# 调用次数和 Token 数趋势 K 线图优化方案

- 阶段：v2.0.60 系列
- 文档时间：2026-08-26
- 适用范围：
  - 管理员 Web（9101）：`/ModelInfo` 模型信息页、`/AgentInfo` Agent 信息页
  - 用户 Web（29001）：`/ModelInfo` 模型信息页、`/AgentInfo` Agent 信息页

## 一、背景与现状

### 1.1 当前实现

| 项 | 现状 |
|---|---|
| 后端 action | `stats`（聚合 summary + models/agents + trend 三合一） |
| 后端 trend 函数 | `GetDailyStatsAll(subTableNum, days)` → 按天桶 (`2006-01-02`) 聚合 |
| 前端 trend 渲染 | 纯 `div` 柱状图，仅 1 条 `count` 维度，颜色蓝/紫渐变 |
| 用户端 trend | 用户端 `userModelInfoInterfaceHandle.stats` / `userAgentInfoInterfaceHandle.stats` 当前**未返回 trend 字段**（只有 admin 返回） |
| 维度 | 仅日期（天）粒度，不支持小时 |
| Tokens 数 | 后端 `DailyStat.TokensTotal` 已返回，但前端只画了 count，未画 Tokens |
| 表大小 | 8 张分表 + keyset 分页扫描（`StatsShardScanBatch=5000`）走 `database.StatsDB()` 25s context |

### 1.2 痛点

1. **趋势粒度太粗**：按天聚合时，30 天只能画 30 根柱子；管理员想看「今天下午 3 点的调用高峰」看不到。
2. **缺失 Tokens 维度**：前端只画了调用次数柱，Tokens 总量作为 tooltip 副标题，没有独立可视化曲线。
3. **慢查询风险**：旧实现 keyset 分页保护到位，但要按小时重算 + 大跨度（如 30 天 × 24 = 720 个桶）会让单次 `scanShardPaged` 拉全表数据，理论上仍可能跑满 25s 超时。
4. **一次性返回**：现状「stats」接口一次性塞 summary/models/trend，前端无法分批加载。

## 二、目标

| # | 目标 | 度量 |
|---|---|---|
| G1 | 趋势粒度细化到**小时** | ≤7 天跨度按小时桶；>7 天按天桶 |
| G2 | 双线趋势：调用次数 + Tokens 数 | K线图/蜡烛图样式（min/max/open/close），含调用次数 + Tokens 两条独立折线 |
| G3 | 无慢查询 | 25s context 保护 + keyset 分页 + 客户端分批请求 |
| G4 | 大跨度数据**动画式**加载 | 客户端先拉 24h → 边渲染边请求后续窗口 |
| G5 | 用户端同样接入 | `userModelInfoInterfaceHandle` / `userAgentInfoInterfaceHandle` 也返回 trend（按本人 + 本人模型过滤） |

## 三、接口设计

### 3.1 复用 + 新增 action

| 接口 | action | 入参 | 返回 | 说明 |
|---|---|---|---|---|
| `ModelInfoInterface` | `stats` | `{days}` | `summary/models/(dst_summary/dst_models)` | **保留不变**（summary/排行/详情用） |
| `ModelInfoInterface` | `trend` | `{hours}` (1~720) | `{points: [{date,count,tokens_total,tokens_input,tokens_output}]}` | **新增**：小时粒度 K 线数据 |
| `AgentInfoInterface` | `stats` | `{days}` | `summary/agents` | 保留不变 |
| `AgentInfoInterface` | `trend` | `{hours}` | `{points: [...]}` | **新增** |

**为什么单独抽 `trend` action：**
- `stats` 返回的 summary/models/agents 数据量大（按用户/模型/Agent 分组聚合），不适合塞 trend；
- `trend` 接口**只看总调用次数与总 Tokens**，更便宜，可被前端反复轮询；
- 前端可按窗口（如最近 24h / 最近 3d / 最近 7d）多次拉取。

### 3.2 响应结构

```json
{
  "success": true,
  "message": "ok",
  "data": {
    "points": [
      {
        "date": "2026-08-26 14:00",
        "count": 123,
        "tokens_input": 45000,
        "tokens_output": 12000,
        "tokens_total": 57000
      }
    ],
    "granularity": "hour",
    "hours": 24,
    "from": "2026-08-25 15:00",
    "to": "2026-08-26 15:00"
  }
}
```

**字段说明：**
- `points[]` 按时间升序，长度 = `hours`（hours≤168 时）或 `days`（hours>168 时按天桶）
- `date` 格式：`"YYYY-MM-DD HH:00"` 或 `"YYYY-MM-DD"`，前端用同一解析逻辑
- `granularity`：`"hour"` 或 `"day"`，告诉前端渲染样式
- `from`/`to` ISO 时间，前端用于坐标轴与对齐

### 3.3 用户端 vs 管理员端

| 维度 | 管理员端 | 用户端 |
|---|---|---|
| 数据源 | 全站 8 张分表 | 仅 `claims.UserName` 对应的 `GetAgentHttpTableName(userName, modelName, subNum)` 表 |
| 过滤 | 无 | `user_name = ?` |
| 表数量 | 8 | `len(modelNames)` |

## 四、后端实现

### 4.1 新增 model 函数（`ServerGo/models/`）

#### 4.1.1 `HourlyTrendPoint`（共用结构）

```go
// HourlyTrendPoint 单时间桶内的调用次数与 Tokens 汇总
type HourlyTrendPoint struct {
    Date         string `json:"date"`
    Count        int64  `json:"count"`
    TokensInput  uint64 `json:"tokens_input"`
    TokensOutput uint64 `json:"tokens_output"`
    TokensTotal  uint64 `json:"tokens_total"`
}

// HourlyTrendResult 趋势响应包装（含粒度 + 时间窗元数据）
type HourlyTrendResult struct {
    Points      []HourlyTrendPoint `json:"points"`
    Granularity string             `json:"granularity"` // "hour" | "day"
    Hours       int                `json:"hours"`
    From        string             `json:"from"`
    To          string             `json:"to"`
}
```

#### 4.1.2 `GetHourlyTrendAll(subTableNum, hours)`（管理员端）

新增到 `ServerGo/models/mysql_http_agent_all_stats.go`：

- 参数 `hours`：
  - `<=0` → 视为 24
  - `>720`（30 天）→ 截断到 720，且强制 `granularity="day"`（720h = 30d）
  - `1~168`（7 天内）→ `granularity="hour"`，桶格式 `"2006-01-02 15:04"`
  - `169~720` → `granularity="day"`，桶格式 `"2006-01-02"`
- 复用 `scanShardPaged`，复用 `database.StatsDB()` 25s context
- SELECT 列：`id, created_at, tokens_input_size, tokens_output_size, tokens_all_size`
- 桶聚合：Go 端按 `created_at.Truncate(time.Hour)` 或 `Format("2006-01-02")` 聚合
- 补齐空桶：从 `now - span` 到 `now` 逐桶 append，缺数据填零
- 返回 `HourlyTrendResult`

#### 4.1.3 `GetHourlyTrendByUser(userName, modelNames, subTableNum, hours)`（用户端）

新增到 `ServerGo/models/subtable.go`（参考 `GetModelInfoUsageStatsByUser` 路由表模式）：

- 仅扫描该用户每个 model 对应的单张分表（`GetAgentHttpTableName`）
- WHERE：`user_name = ?` （已由 routing 保证只命中该用户的表）
- 其它逻辑与 `GetHourlyTrendAll` 一致

### 4.2 API handler 改动

##### `server_api_manager_model_info.go` / `server_api_manager_agent_info.go`

新增 case `"trend"`：

```go
case "trend":
    hours := req.Hours  // 新增字段 Hours
    if hours <= 0 { hours = 24 }
    res, err := modelsdb.GetHourlyTrendAll(config.G.DBMysqlSubTableNumber, hours)
    if err != nil { /* log + return error */ }
    json.NewEncoder(w).Encode(userManageResp{Success: true, Data: res})
```

请求结构扩展：

```go
var req struct {
    Action string `json:"action"`
    Days   int    `json:"days"`
    Hours  int    `json:"hours"`  // 新增
}
```

##### `server_api_user_model_info.go` / `server_api_user_agent_info.go`

新增 case `"trend"`：调用 `GetHourlyTrendByUser(claims.UserName, modelNames, subTableNum, hours)`，JWT claims 保证越权防护。

### 4.3 慢查询防护（4 重保险）

| # | 措施 | 实现位置 |
|---|---|---|
| 1 | 25s context（驱动级 KILL） | `database.StatsDB()` → 新函数内 `sdb, cancel := database.StatsDB()` |
| 2 | keyset 分页（每批 5000 行） | 复用 `scanShardPaged(sdb, tableName, "id, created_at, tokens_...", hours, fn)` |
| 3 | `created_at >= cutoff` 预过滤 | `scanShardPaged` 已支持 `days > 0` 时加 cutoff；本接口 hours 也走同一 helper |
| 4 | `Hours` 上限截断 | 720h = 30d，再大强制按天桶，避免「小时精度 × 多年」撑爆内存 |

### 4.4 单测要求

新增 `ServerGo/models/hourly_trend_test.go`：
- 空表 → 返回零桶数组
- 1 张分表 50 行混合 2 个小时 → 2 桶聚合正确
- hours=0 → 默认 24 小时
- hours=1000 → 截断到 720 且 granularity=day
- ctx 超时（注入假慢查询）→ 返回部分结果或超时 err，不 panic
- 用户端 `GetHourlyTrendByUser`：仅扫该用户的表，无 user/model 时返回零

## 五、前端实现

### 5.1 新增组件：`KLineTrendChart.jsx`

路径：`ClientWeb/src/components/KLineTrendChart.jsx`

**技术约束：** 沿用工程惯例——**不引入第三方图表库**（无 echarts/recharts/d3）。用纯 SVG 自研双线趋势图。

**功能要点：**
- props：`points`（数组）、`title`、`height`（默认 280）
- 渲染：
  - 上半区：调用次数折线（左 Y 轴，单位「次」）
  - 下半区：Tokens 折线（右 Y 轴，单位「Tokens」），可切换为共用坐标
  - X 轴：自动按时间窗选择刻度密度（≤24 个点全显示；25~168 个点按小时聚合显示日期 + 小时；>168 只显示日期）
  - hover 十字线 + 浮窗显示 `count`、`tokens_total`、`tokens_input/output`
- 动画：
  - 入场：`stroke-dasharray` + `stroke-dashoffset` 由大到小（SVG path animation），duration 800ms
  - 数据更新：新点 fade-in，旧点 slide 渐变
- 暗色/亮色主题：读 CSS 变量 `--trend-color-1/2`

### 5.2 组件：`HourlyTrendPanel.jsx`

封装 K 线图 + 时间窗切换 + 加载态：

```jsx
<HourlyTrendPanel
  api="ModelInfoInterface"
  title={t('modelInfo.callTrend')}
  windowOptions={[24, 72, 168, 720]}   // 1d / 3d / 7d / 30d
  defaultWindow={24}
  tokenLabel={t('modelInfo.tokensUnit')}
  callLabel={t('modelInfo.callsUnit')}
/>
```

- 切窗时**重新拉数据**，不带缓存（沿用工程风格，stats 类接口无服务端缓存）
- 加载态：顶部 shimmer 横条 + 半透明遮罩
- 空数据：友好文案（沿用 i18n）

### 5.3 接入 `ModelInfo.jsx` / `AgentInfo.jsx`

替换原 `<div className="card">` + 柱状 trend 块：

```diff
- {trend.length ? (
-   <div className="card">
-     <h3>{t('modelInfo.callTrend')}</h3>
-     <div style={{ display:'flex', alignItems:'flex-end', gap:6, height:160 }}>
-       {trend.map(s => ( ... 柱状 ... ))}
-     </div>
-   </div>
- ) : null}
+ {models.length || dstModels.length ? (
+   <div className="card">
+     <h3>{t('modelInfo.hourlyTrend')}</h3>
+     <HourlyTrendPanel
+       api="ModelInfoInterface"
+       title={t('modelInfo.hourlyTrend')}
+       windowOptions={[24, 72, 168, 720]}
+       defaultWindow={24}
+     />
+   </div>
+ ) : null}
```

**用户端要点：**
- 由于旧 `stats` 不返回 trend，前端 `useEffect` 不再依赖 `data.trend`
- 改为 `HourlyTrendPanel` 内部按 `api + action:'trend' + hours` 自管请求

### 5.4 分批 + 动画式加载

为防止 hours=720 时一次性拉 720 个桶（图表卡片闪一下才出），前端分两段：

```
0~24h → 立即渲染
24h~168h → 用户切换窗口或 5s 后 lazy 拉取并接入（同图合并 + 滚动 viewport）
```

- 用 `window.requestIdleCallback` 在 idle 时预取大窗口
- 拆批 UI：顶部分段控件 [1d] [3d] [7d] [30d]，按钮 disabled 时显示 spinner

## 九、风险与回退

| 风险 | 应对 |
|---|---|
| 客户端 SVG 在 720 桶下卡顿 | X 轴降采样 + 视图端口虚拟化 |
| 用户端跨表查询变慢 | 用户端仅扫本用户模型对应的表（≤几十张，且每张只走自己路由） |
| 新接口未注册 | 阶段 5 编译 + 路由表确认（沿用 `RegisterManagerAPIRoutes`/`RegisterUserAPIRoutes`） |
| 旧 `stats` 仍返回 trend | 保留兼容，前端 `ModelInfo.jsx` 不再读取 `data.trend`，改为新接口 |
