# 源站管理工作时间功能升级方案

> 创建日期：2026-09-15
> 状态：已实施
> 关联需求：源站管理添加工作时间功能（0-24 全天 / 多段工作时间 / 精确到秒）

---

## 1. 需求概述

为 `TAgentDstEndPoint`（源站接入点）增加"工作时间"能力：

1. 每个源站可配置多段工作时间（开始时间–结束时间），**精确到秒**
2. `00:00:00 - 24:00:00` 表示全天 24 小时工作；支持多段如 `00:00:00-01:00:00`、`23:00:00-24:00:00`
3. 后台定时协议按当前时间自动启用/禁用源站（工作时间内可用，非工作时间禁用）
4. 管理端 + 用户端 `源站管理` 页面展示工作时间字段
5. 管理端添加/编辑弹窗支持配置工作时间
6. 数据库 `TAgentDstEndPoint` 表新增工作时间字段与索引
7. 现有数据补全脚本（默认全天 24 小时），保存到 `tmpPlan/`（不提交 git）
8. 添加源站默认值：全天 24 小时

## 2. 数据模型设计

### 2.1 TAgentDstEndPoint 新增字段

```go
// WorkPeriods 工作时间段列表（JSON 数组），每段 {start: "HH:MM:SS", end: "HH:MM:SS"}
// 默认值 [{"start":"00:00:00","end":"24:00:00"}] 表示全天工作
// 多段示例 [{"start":"00:00:00","end":"01:00:00"},{"start":"23:00:00","end":"24:00:00"}]
WorkPeriods string `json:"work_periods" gorm:"column:work_periods;size:512;comment:工作时间段JSON，格式[{\"start\":\"HH:MM:SS\",\"end\":\"HH:MM:SS\"}]"`

// WorkStatus 工作时间驱动的实际可用状态（内存计算 + 持久化兜底）：
//   1=当前在工作时间内（可用），0=当前在非工作时间（禁用）
//   后台定时协议每分钟刷新；仅当 WorkPeriods ≠ 全天时参与路由选择
WorkStatus int `json:"work_status" gorm:"column:work_status;default:1;index;comment:工作时间状态:1=在工作时间,0=非工作时间"`
```

### 2.2 索引设计

- `work_status`：单列索引（路由选择过滤 + 后台任务筛选）
- `status`：已有索引（用户启停）
- 复合索引 `(user_id, status, work_status)`：管理端按用户列表查询 + 代理热路径过滤

### 2.3 时间格式

- 存储格式：`HH:MM:SS`（24 小时制），`24:00:00` 表示当天结束（即 86400 秒）
- 字段类型：`size:512`（足够容纳多段 JSON）
- 精度：秒级

## 3. 后端架构设计

### 3.1 新增模型层文件

`ServerGo/models/endpoint_work_periods.go`：

```go
type WorkPeriod struct {
    Start string `json:"start"` // "HH:MM:SS"
    End   string `json:"end"`   // "HH:MM:SS"（允许 24:00:00）
}

// ParseWorkPeriods 解析 JSON → []WorkPeriod
// ValidateWorkPeriods 校验格式、时间范围、start < end
// FormatWorkPeriods []WorkPeriod → JSON
// IsInWorkPeriods(now time.Time, periods []WorkPeriod) bool 当前时间是否在任一工作时间段内
// DefaultWorkPeriods() → [{"start":"00:00:00","end":"24:00:00"}] 全天
```

### 3.2 后台定时协议

`ServerGo/models/endpoint_work_scheduler.go`：

- `StartEndpointWorkScheduler(ctx context.Context, interval time.Duration)`：启动后台 goroutine
- 每分钟（默认）遍历缓存中所有源站，计算当前是否在工作时间内
- 若 `WorkStatus` 与计算结果不一致，更新 DB + 缓存 + 同步路由状态列表
- 使用 `time.NewTicker` + `ctx.Done()` 优雅退出（与 spider scheduler 同模式）
- 仅当 `WorkPeriods ≠ 全天` 时才触发启停（全天 = 不干预，保持 status 原值）

### 3.3 路由选择集成

代理热路径（`server_http_ai_proxy_utils.go` L412-427）已检查 `dstEndpoint.Status == 0`，无需修改。
经济型算法（`agent_algorithm_economic.go` L754-780）`isEndpointEnabled` 检查 `ep.Status == 0`，无需修改。

关键点：**后台协议直接修改 DB 的 `status` 字段**，这样现有的 `Status == 0` 检查自动生效，代理无需任何改动即可实现"工作时间外自动禁用"。

具体策略：
- 后台任务修改 `status` 字段（0/1）实现自动启停
- 同时维护 `work_status` 字段作为"时间驱动状态"的持久化快照
- 管理端展示的 `status` 是"用户启停"（toggle_status），后台任务启停走独立逻辑

**最终策略**：
- 引入 `auto_work_status` 概念：后台任务只管理"工作时间内的可用性"
- 实际 status = `user_status AND work_status`（用户启用 且 在工作时间 = 启用）
- 但 status 是单一字段，需编码决策：

**简化决策**：后台任务直接修改 `status`。当用户启用 + 在工作时间 → status=1；用户启用 + 非工作时间 → status=0；用户手动禁用 → 保持 status=0 且后台任务不覆盖。

实现：记录"用户手动设置的状态"，后台任务只在"用户手动启用"前提下修改 status。

```go
// status 语义：
//   0 = 禁用（用户手动禁用 或 当前非工作时间）
//   1 = 启用（用户手动启用 且 当前在工作时间 或 全天工作）
//
// 后台任务逻辑：
//   if user_status == 0: 不干预（用户手动禁用优先）
//   else:
//     if 在工作时间 or 全天: status = 1
//     else: status = 0
```

为此需要拆分 status 为两个字段：
- `status`（已有）：用户手动启停（toggle_status 管理）
- `work_status`（新增）：工作时间状态（后台任务管理）

**代理热路径改造**：在 `server_http_ai_proxy_utils.go` 选择源站时，条件从 `dstEndpoint.Status == 0` 改为 `dstEndpoint.Status == 0 || dstEndpoint.WorkStatus == 0`。

这样：
- 用户禁用 → status=0 → 不可用 ✓
- 非工作时间 → work_status=0 → 不可用 ✓
- 全天工作 → work_status 恒为 1 → 由 status 决定 ✓
- 管理员 toggle 只改 status，不会被后台任务覆盖 ✓
- 后台任务只改 work_status ✓

## 10. 关键约束

- 时间精度到秒（`HH:MM:SS`）
- `24:00:00` 作为结束时间合法
- 后台任务每分钟执行，不影响代理热路径性能（只读缓存 + 按需写 DB）

- 全天工作（默认值）→ work_status 恒为 1，后台任务不干预 status
- 现有数据迁移默认全天

## 11. 需求 #12 补充：工作时间启用/禁用开关（2026-09-15 第二阶段）

### 11.1 字段设计

`TAgentDstEndPoint` 新增：

```go
// WorkEnabled 工作时间功能开关：1=启用（按 WorkPeriods 时间段控制可用性），
// 0=禁用（工作时间功能不生效，0-24 全天可用，WorkStatus 恒为 1）。
// 禁用时不删除 WorkPeriods 配置，便于重新启用时恢复原时间段。
WorkEnabled int `json:"work_enabled" gorm:"column:work_enabled;default:1;index;comment:工作时间开关:1=启用时间段控制,0=禁用(全天可用)"`
```

### 11.2 语义

| WorkEnabled | 行为 |
|---|---|
| 1（启用，默认） | 按现状：工作时间内可用，非工作时间 work_status=0 自动禁用 |
| 0（禁用） | 工作时间功能整体不生效：0-24 全天可用，work_status 恒为 1；WorkPeriods 配置保留不删 |

### 11.3 实现要点

1. **Scheduler**：`WorkEnabled==0` 的源站跳过时间段计算，work_status 兜底修正为 1。
2. **Add**：Create 改用 `Select(...)` 显式列（含 work_enabled），避免 gorm `default:1` 把显式 0 覆盖为 1（零值陷阱）。
3. **Update**：work_enabled 始终写入；`WorkEnabled=0` 时 work_status 立即置 1（不等 scheduler 下一轮）；API 层用 `*int` 指针区分"未提供"（保留原值，兼容旧客户端）与"明确禁用"（0）。
4. **代理热路径 / 经济型算法**：无需改动——它们检查 `WorkStatus == 0`，禁用时 work_status 恒 1 自然放行。
5. **前端**：
   - 列表列：禁用时显示"全天"+ "已停用"徽标 + 状态点恒绿；悬停完整信息含禁用提示行。
   - 弹窗：新增"工作时间控制"复选开关（启用:按时间段自动启停 / 禁用:全天可用）；禁用时时间段编辑区整体置灰只读 + 显示禁用提示；禁用状态下跳过时间段校验（保留配置）。
6. **i18n**：三语新增 workEnabled / workEnabledOn / workEnabledOff / workDisabledTag / workDisabledTip。

### 11.4 API 变更

管理端请求：`work_enabled`（int 0/1，缺省=保留原值）；响应 list：`work_enabled`。
用户端 list 响应：`work_enabled`（只读展示）。

### 11.5 数据迁移

迁移脚本新增 `work_enabled int NOT NULL DEFAULT 1` 列 + `idx_work_enabled` 索引；现有数据默认 1（启用），配合已有全天 work_periods 行为不变。
