## 一、背景与目标

阶段DA（v2.0.86）已完成「删除自动刷新」「删除模型下拉」「7 天时段画像 + 时段带 + 峰谷」
三项改造。本阶段按用户再次明确的 11 条要求继续优化，核心增量是：

1. **补齐近 1 个月维度**：页面要有「近 1 天（逐时段）/ 近 1 周（逐时段）/ 近 1 个月（逐时段）」
   三套统计与图表，而不是只到 7 天。
2. **模型状态总览真正图表化**：不再只是文字统计卡，要有统计条、横向比较、峰谷标注、
   每模型小倍数，让「各个源站的区别」一眼可见。
3. **排队拥堵与质量横向差异量化**：给出每源站相对全站中位数的偏差（+x% / -x%），
   而不是只列各自数值。
4. 保持阶段DA 已删除的「自动刷新」「模型下拉」不再回归。

   ├ 最好 / 最差源站结论行（文字 + 数值，不靠颜色单独传意）

④ 时段带 × 模型 横向比较（跟随统计窗口；6 时段带 × N 模型）
⑤ 运行经验预测（全模型，无下拉：下一时段条 + 明日表 + 小倍数折线）
⑥ 模型质量对比（跟随统计窗口；6 指标横向条形）

> 设计原则：**一个筛选器只放在它所统辖的图表之上**。统计窗口与趋势窗口语义不同
>（前者是「汇总统计区间」，后者是「趋势曲线粒度」），因此分两组但共用同一行，并在
> 每组前显示文字标签，避免「一个下拉管一半」的困惑。

## 三、数据源研读：`TAgentHttpTransactionDataItem`

表定义：`ServerGo/models/mysql_http_agent_model.go:102`（分表 `TAgentHttpTransactionDataItem_%02d`，
8 张，按 `user_name` + `model_name` 哈希分片）。

| 字段 | 落库实况 | 本阶段用法 |
|---|---|---|
| `request_start_at` | 用户发起调用的真实时刻 | **唯一时间轴**：时段画像 / 峰谷 / 窗口统计 |
| `created_at` | ≈ `request_start_at` + 响应耗时 + 落库延迟 | 仅作 `request_start_at` 异常时兜底 |
| `request_end_at` / `response_start_at` | 代理路径写成 `request_start_at` 副本 | 不使用（TTFB 恒 0） |
| `response_end_at` | 真实完整响应时刻 | 不使用（≈ elapsed 冗余） |
| `elapsed_ms` | 端到端总耗时 | 时延口径 + 归一化拥堵系数分子 |
| `tokens_output_size` | 输出 Token | 归一化分母（10 档对数分箱） |
| `response_status` | 状态文本 | 2xx / 429 / 5xx / 其他 分类 |
| `dst_model_name` | 源站模型 | 聚合主键（空值行跳过） |
| `dst_endpoint_id` | 源站接入点 | 备用维度，本阶段不拆 |
| `user_name` | 用户 | 用户端隔离 |

**拥堵系数口径**：`elapsed_ms ÷ (该输出 Token 分档的 7 天基准 ms/Token × 输出 Token)`。
无直接排队时间可测，该系数是「相对该源站自身 7 天基准」的排队/降速程度：
≈1 正常、1.2–2 轻度、2–5 中度、>5 严重。

> ⚠️ 基准必须固定为近 7 天：若基准随扫描窗口变成 30 天，同一请求的系数会变化，
> 历史对比与告警阈值（1.2/2/5）都会失真。因此本阶段**扫描 30 天，但基准仍只取近 7 天**。

## 四、后端设计（`ServerGo/models/mysql_http_agent_qos_stats.go`）

### 4.1 窗口常量

```go
qosScanWindow     = 30 * 24 * time.Hour // 扫描（近 1 个月视图）
qosBaselineWindow = 7 * 24 * time.Hour  // 拥堵系数基准（固定 7 天）
qosForecastWindow = 7 * 24 * time.Hour  // 运行经验预测（固定 7 天同时段历史）
```

扫描仍走 `database.StatsDB()` 25s context；超时返回已聚合部分（既有语义）。

### 4.2 新增数据结构

```go
// QoSWindowView 单个统计窗口（24h/7d/30d）的完整视图，前端一次取用。
type QoSWindowView struct {
    Window      string           `json:"window"`
    Stats       QoSWindowStats   `json:"stats"`
    HourProfile []QoSHourProfile `json:"hour_profile"` // 24 点（窗口内同时段汇总）
    Bands       []QoSTimeBand    `json:"bands"`        // 6 业务时段带
    PeakValley  QoSPeakValley    `json:"peak_valley"`
    Trend       []QoSBucketPoint `json:"trend"` // 24h→24 小时桶；7d/30d→7/30 天桶
}
```

`QoSModelReport` 新增：

```go
Stats30d       QoSWindowStats              `json:"stats_30d"`
HourProfile24h []QoSHourProfile            `json:"hour_profile_24h"`
HourProfile30d []QoSHourProfile            `json:"hour_profile_30d"`
Bands30d       []QoSTimeBand               `json:"bands_30d"`
PeakValley24h  QoSPeakValley               `json:"peak_valley_24h"`
PeakValley30d  QoSPeakValley               `json:"peak_valley_30d"`
Days30d        []QoSBucketPoint            `json:"days_30d"`

Windows        map[string]QoSWindowView    `json:"windows"`
```

`QoSMonitorReport` 新增：

```go
TotalCalls30d int64                    `json:"total_calls_30d"`
Windows       map[string]QoSWindowView `json:"windows"` // 全站口径（跨模型加权）
```

既有字段（`stats_24h`/`stats_7d`/`hour_profile`/`bands_*`/`peak_valley`/`days`）
**语义保持不变**，保证旧前端/旧脚本兼容；新前端优先读 `windows`。

### 4.3 扫描与计数

- `cutoff = now - 30d`；
- `calls7d` / `okCalls7d` 只在 `ts >= now-7d` 时累加（**修复**：扫描窗口扩大后不能让 7 天指标变成 30 天）；
- 新增 `calls30d` / `okCalls30d`（全扫描窗口）；
- 基准（全局 + Token 分档）只在 `ts >= now-7d` 且 2xx/输出>0/耗时>0 时累加；
- 小时桶保留全部 30 天（`m.hours` ≤ 720 个桶）；
- 分钟桶仍只保留最近 60 分钟。

### 4.4 窗口化聚合

```go
buildQoSHourProfileRange(m, base, now, since) // 按小时归并 [since, now] 内的小时桶
buildQoSWindowStats(m, base, now, "30d", now.Add(-30d))
buildQoSTimeBands(...)                         // 复用既有实现
buildQoSPeakValley(profile, bands, nil)        // 峰/谷随窗口变化
buildQoSDaySeriesN(m, base, now, 30)           // 近 30 天逐日桶（days_30d）
```

每个模型构建：

| 窗口 | 统计 | 小时画像 | 时段带 | 峰谷 | 趋势序列 |
|---|---|---|---|---|---|
| 24h | `stats_24h` | `hour_profile_24h` | `bands_24h` | `peak_valley_24h` | `hours` (24) |
| 7d | `stats_7d` | `hour_profile` (既有字段) | `bands_7d` | `peak_valley` (既有) | `days` (7) |
| 30d | `stats_30d` | `hour_profile_30d` | `bands_30d` | `peak_valley_30d` | `days_30d` (30) |

> 24h 画像的 `days` 为 1（每个小时只出现一次），`avg_calls_per_day` 即该小时调用量；
> 7d/30d 画像按「该小时有数据的天数」归一，避免某模型只在少数天有流量被摊薄成假低谷。

### 4.5 预测与 7 天口径修正

- `buildQoSPrediction` 两遍循环都只处理 `key >= now-7d` 的小时桶
  （否则 30 天扫描会把「近 7 天同时段历史」悄悄变成 30 天）。
- `qosWeekPercentiles` 同理只取近 7 天小时桶。
- `buildQoSHeatmap` 仍只取近 7 天（日期映射天然跳过更早的行）。
- `today_vs_week`、`tomorrow`、`trend_24h` 语义不变。

### 4.6 全站窗口汇总

新增 `aggregateQoSWindows(models)`：

- 调用量 / 成功数 / 错误数：求和；
- 拥堵系数：Σ(模型系数 × 模型样本) / Σ 样本（**跨模型样本加权，不混算耗时**）；
- 错误率：Σ(模型错误率 × 模型调用) / Σ 调用；
- 成功平均时延：成功数加权；
- P95：取各模型最大值（全站最差体验，保守口径）；
- 小时画像按模型画像归并；时段带由归并后画像重算；峰谷由全站画像重算；
- 趋势序列按桶聚合（同口径加权）。

### 4.7 性能估算

| 项 | 近 7 天（旧） | 近 30 天（新） |
|---|---|---|
| 扫描行数（生产实测） | 41,566 | 62,384 |
| 内存 pairs（elapsed+tokens+ok） | ~1.0 MB | ~1.5 MB |
| 画像计算 | 24×3 次归并 | 24×3 次归并（桶数 ≤720） |
| 预估接口耗时 | 0.4s | < 1s |

缓存仍为 60s，手动刷新 `{"refresh":true}` 旁路。

### 5.2 新增 `QoSWindowStats.jsx`（模型状态总览 · 统计）

- **全站窗口统计条**：调用、成功率、拥堵系数、错误率、成功均值、P95、高峰、低谷；
- **源站横向比较表**（核心）：
  - 排名（按拥堵系数降序，低样本置底）；
  - 模型名（稳定分类色点）；
  - 拥堵系数条 + 数值 + 状态文字；

- **最好 / 最差结论行**：文字给出拥堵最低与最高源站及偏差；

## 七、测试计划

### 7.1 Go 单元测试（新增）

1. **30 天扫描**：20 天前的请求进入 `stats_30d`/`hour_profile_30d`，但不进入 `stats_7d`/`calls_7d`；
2. **基准仍为 7 天**：20 天前的极端耗时样本不得改变 `baseline_ms_per_token`；
3. **窗口画像**：24h/7d/30d 的 `calls` 分别等于对应窗口小时桶调用总和；
4. **30 天逐日序列**：`len(days_30d) == 30`，首日 = 29 天前，末日 = 今天；
5. **窗口峰谷**：构造 20 天前 3 时为峰、近 7 天 14 时为峰 → `peak_valley_30d.peak_hour==3` 且 `peak_valley.peak_hour==14`；

8. **周分位不跨 30 天**：20 天前超慢样本不改变 `week_ok_p95_ms`。
