# 用户日志模块数据库持久化重构方案（2026-08-25）

> 背景：当前"用户日志"功能基于纯文本文件 `LsmTokensServerUsersInfo.log`，通过 `logger.LogUserAction()` 写入，前端 `UserLogDialog` 以 monospace 纯文本方式展示。
> 该方案存在文件全量读取效率低、无法按字段精确筛选、展示形式单调、无自动容量控制等问题。
> 本方案将其迁移到 **MySQL 数据库持久化**，支持结构化分页查询与美观 DataTable 表格展示。

## 1. 现状分析

### 1.1 数据流

```
Go 操作（登录/增删改源站/路由切换等）
  → logger.LogUserAction(actionType, username, details)
  → 追加写入 LsmTokensServerUsersInfo.log（纯文本行）
  → 前端 POST /UserInfoLogInterface → 全量读取文件 → 内存解析排序 → 分页返回
  → 前端 UserLogDialog monospace 文本展示
```

### 1.2 已记录的操作类型（16 种）

| 操作类型 | 来源文件 | 说明 |
|---------|---------|------|
| `LOGIN` | server_api_user_login.go | 用户登录 |
| `MANAGER_LOGIN` | server_api_manager_login.go | 管理员登录 |

### 1.3 现有问题

- **性能**：每次查询全量读取文件→内存解析→排序（文件越大越慢）
- **筛选**：仅支持全字段关键词模糊匹配，无法按操作类型/用户精确筛选
- **展示**：纯文本 monospace，无结构化列，无法排序
- **容量**：无自动清理机制，文件只增不减

## 2. 数据库表设计

### 2.1 表结构

**表名：** `TAgentUserOperationLog`（遵循 `T` + PascalCase 命名惯例）

```go
type TAgentUserOperationLog struct {
    ID         uint64    `json:"id" gorm:"primaryKey;autoIncrement;comment:主键ID"`
    CreatedAt  time.Time `json:"created_at" gorm:"not null;index;comment:操作时间"`
    ActionType string    `json:"action_type" gorm:"size:32;index;comment:操作类型"`
    UserName   string    `json:"user_name" gorm:"size:50;index;comment:操作用户"`
    Details    string    `json:"details" gorm:"size:2048;comment:操作详情"`
}
```

### 2.2 设计要点

- **不设 `UpdatedAt`/`DeletedAt`**：日志只增不改不软删，简化存储
- **三列索引**：`CreatedAt`（时间排序）、`ActionType`（按类型筛选）、`UserName`（按用户筛选）
- **复合索引**：`idx_action_user_created (action_type, user_name, created_at)` 加速组合查询
- **容量上限**：10 万条记录，超限自动删除最老的 1 万条
- **字符集**：默认 utf8mb4，Details 存中文操作详情

### 2.3 容量控制策略

在 `AddUserOperationLog` 写入时维护内存计数器（原子变量），每 100 次写入检查一次总记录数：
- 超过 100,000 条时，`DELETE FROM TAgentUserOperationLog ORDER BY created_at ASC LIMIT 10000`
- 使用硬删除（`Unscoped`），避免软删除残留
- 非阻塞：清理在后台 goroutine 执行，不阻塞写入

## 3. 后端实现

### 3.1 新建：`ServerGo/models/mysql_user_operation_log.go`

| 函数 | 说明 |
|------|------|
| `InitUserOperationLogTable()` | AutoMigrate 建表 |
| `AddUserOperationLog(actionType, userName, details)` | 写入单条记录 + 触发容量检查 |
| `QueryUserOperationLogs(page, pageSize, keyword, actionType, userName)` | 分页查询，支持多条件筛选 |
| `CleanupOldOperationLogs()` | 删除超限的最老记录 |

### 3.2 修改：`ServerGo/logger/logger.go`

- 新增回调变量 `var DBLogWriter func(actionType, userName, details string)`
- `LogUserAction()` 中文件写入之后，异步调用 `go DBLogWriter(...)` 写入数据库
- 回调注入方式避免 `logger` → `models` 循环依赖

### 3.3 修改：`ServerGo/main.go`

在数据库初始化成功后注入回调：
```go
if err := modelsdb.InitUserOperationLogTable(); err != nil {
    logger.Printf("[WARNING] Failed to init user operation log table: %v", err)
} else {
    logger.DBLogWriter = modelsdb.AddUserOperationLog
}
```

### 3.4 修改：`ServerGo/api/server_api_common_extra.go`

**请求参数扩展：**

| 参数 | 类型 | 说明 |
|------|------|------|
| `page_num` | int | 页码，从 1 开始 |
| `page_size` | int | 每页条数，默认 20，可选 10/20/50/100 |
| `search_keyword` | string | 关键词（对 action_type + user_name + details 模糊匹配） |
| `action_type` | string | 操作类型精确筛选（可选） |
| `user_name` | string | 用户名精确筛选（可选） |

**响应格式：**

```json
{
  "success": true,
  "records": [
    {
      "id": 123,
      "created_at": "2026-08-25 08:16:19",
      "action_type": "LOGIN",
      "user_name": "liusm191",
      "details": "密码登录 IP=192.168.1.100"
    }
  ],
  "total_count": 1500,
  "total_pages": 75,
  "page_num": 1,
  "page_size": 20
}
```

- 数据库未初始化时降级为空结果（不影响启动）
- 删除旧的 `UserLogReader` 文件读取逻辑（约 350 行）

## 5. 兼容性说明

- **文件日志保留**：`LogUserAction` 继续写入文件（兼容现有日志分析工具/脚本），数据库写入为异步附加
- **API 接口兼容**：保留 `UserInfoLogInterface` 路由名不变，请求参数向后兼容（新增参数可选）
- **数据库未配置降级**：`database.DB == nil` 时 `AddUserOperationLog` 静默跳过，API 返回空结果
- **双端共用**：管理端（9101）和用户端（29001）的 `/UserInfoLogInterface` 均改为数据库查询
