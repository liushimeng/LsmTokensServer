# 代理 x-api-key 头认证兼容与相关请求头转发升级方案

> 版本：阶段CW（v2.0.79）
> 日期：2026-10-19
> 涉及包：`ServerGo/proxy`、`ServerGo/protocol`

## 一、背景与问题定位

DeepSeek Harness Agent（DSH）接入本服务 AI 代理（29000 端口 `/Anthropic` 路由）时全部请求 401，
经逐条实测定位：

- DSH 的 `anthropic-messages` 协议（pi-ai SDK，遵循 Anthropic 官方约定）**只发送 `x-api-key` 头**，
  不发送 `Authorization: Bearer` 头；
- 本服务代理鉴权中间件 `extractAPIKey`（`proxy/server_http_ai_proxy_utils.go`）**只认
  `Authorization: Bearer`，`x-api-key` 一律 401 `missing Authorization header`**；
- CORS 预检虽然允许 `x-api-key`，但鉴权链路本身不收——属于代理实现的约定偏差。

对照实验结论（与 DSH 侧分析报告一致）：

| 请求形态 | 结果 |
|---|---|
| 仅 `x-api-key: $KEY` | 401 missing Authorization header |
| 仅 `Authorization: Bearer $KEY` | 200 |
| 两个头同时携带 | 200 |

另外发现次要问题：CORS 预检响应 `Access-Control-Allow-Headers` 只声明了
`Content-Type, Authorization, anthropic-version, x-api-key`，**缺少 `anthropic-beta`、
`openai-beta`、`x-request-id`**。服务端头转发白名单（`protocol/header_forward.go`）虽已放行
这三个头，但浏览器类客户端在预检阶段就会被 CORS 拦截，转发白名单形同虚设。

## 二、影响面分析

### 2.1 现状代码链路

```
handleAIProxyRequest (proxy/server_http_ai_proxy.go:231)
  └─ extractAPIKey (proxy/server_http_ai_proxy_utils.go:23)   ← 问题点①：仅读 Authorization
  └─ forwardWithRetry
       └─ copySafeProxyRequestHeaders (proxy/server_http_ai_proxy_security.go:149)
            └─ protocol.ShouldForwardProxyHeader (protocol/header_forward.go:15)
               白名单已含：anthropic-version / anthropic-beta / openai-beta /
                          x-request-id / user-agent / x-stainless-* / openai-*
               双向丢弃：authorization / x-api-key / api-key / cookie / 转发链 / hop-by-hop
setCORSHeaders (proxy/server_http_ai_proxy_utils.go:879)     ← 问题点②：预检声明不全
```

### 2.2 兼容性约束

1. **Authorization 优先级不变**：两个头同时存在时仍以 `Authorization: Bearer` 为准（与 DSH
   实测"两个头并存返回 200"一致，行为不回退）。
2. **API Key 格式校验不变**：`isValidProxyAPIKeyFormat`（sk- 前缀或 UUID 形态）在 fallback
   之后统一执行，暴力猜测防护、失败限流（`proxyAuthFailureLimiter`）逻辑不动。
3. **客户端密钥头不转发上游**：`x-api-key`/`authorization` 仍在上游转发层丢弃、改写为源站
   自身凭据（`proxyReq.Header.Set("Authorization", "Bearer "+dstEndpoint.APIKey)`），
   安全红线不松动。
4. **上游出站头只用源站 APIKey**：fallback 提取的 key 仅用于本服务鉴权与模型路由查询，
   不会泄露到上游。

## 三、实施方案

### 3.1 问题点①：`extractAPIKey` 增加 x-api-key 回退（核心）

`proxy/server_http_ai_proxy_utils.go`：

```go
// extractAPIKey 从请求头提取 API Key（Anthropic 协议客户端只发 x-api-key，兼容回退）
func extractAPIKey(r *http.Request) (string, error) {
    // 1. 优先 Authorization: Bearer（既有行为，优先级最高）
    if auth := r.Header.Get("Authorization"); auth != "" {
        parts := strings.SplitN(auth, " ", 2)
        if len(parts) != 2 || !strings.EqualFold(parts[0], "Bearer") {
            return "", fmt.Errorf("invalid Authorization format, expected 'Bearer {api_key}'")
        }
        key := strings.TrimSpace(parts[1])
        if key == "" {
            return "", fmt.Errorf("empty API Key")
        }
        return key, nil
    }
    // 2. 回退 x-api-key（Anthropic 官方 SDK / DSH anthropic-messages 的标准做法）
    if apiKey := r.Header.Get("X-Api-Key"); apiKey != "" {
        // 兼容整行粘贴 "Bearer sk-..." 的客户端，剥离 Bearer 前缀
        key := strings.TrimSpace(apiKey)
        key = strings.TrimPrefix(key, "Bearer ")
        key = strings.TrimPrefix(key, "bearer ")
        if key == "" {
            return "", fmt.Errorf("empty API Key")
        }
        return key, nil
    }
    return "", fmt.Errorf("missing Authorization or x-api-key header")
}
```

要点：
- `Authorization` 存在但格式非法时**不**回退到 x-api-key——显式带了非法头说明客户端意图
  是 Bearer，静默回退会掩盖配置错误；
- `x-api-key` 值剥离可选 `Bearer ` 前缀（与 `system/ai_api_connectivity.go` 的
  `resolveAuthHeaders` 既有约定对齐，用户从请求头整行粘贴也能用）；
- 错误文案改为 `missing Authorization or x-api-key header`，便于客户端排查。

### 3.2 问题点②：CORS 预检声明补全

`proxy/server_http_ai_proxy_utils.go` 的 `setCORSHeaders`：

```
Access-Control-Allow-Headers: Content-Type, Authorization, x-api-key, api-key,
    anthropic-version, anthropic-beta, openai-beta, x-request-id, x-stainless-*
```

与 `protocol.ShouldForwardProxyHeader` 放行集合对齐（`x-stainless-*` 以通配声明，
Anthropic SDK 的 `x-stainless-arch/os/package-version/lang` 等运行时头族）。

### 3.3 测试用例

`proxy/server_http_ai_proxy_logic_test.go` 的 `TestExtractAPIKey` 扩充：

| 用例 | 头 | 期望 |
|---|---|---|
| x-api-key 基本 | `X-Api-Key: sk-test123` | `sk-test123` |
| x-api-key 带 Bearer 前缀 | `X-Api-Key: Bearer sk-test123` | `sk-test123` |
| 双头并存 Authorization 优先 | Auth=`Bearer sk-a` + x-api-key=`sk-b` | `sk-a` |
| Authorization 非法格式不回退 | Auth=`Basic xx` + x-api-key=`sk-b` | 报错 |
| 双头缺失 | 无 | 报错（文案含两个头名） |

`protocol` 包头转发白名单行为不变，已有测试覆盖。

   - 仅 `Authorization: Bearer` → 200（回归）；

   - 无认证头 → 401，message 为 `missing Authorization or x-api-key header`。

## 五、不改的事项（显式排除）

- 不改上游出站头策略（客户端密钥永不上送）；
- 不改 API Key 格式校验、失败限流阈值；
- DSH 侧无需改配置（不需要把 key 复制进 `cordis.patch.yml` headers），方案 B 一步到位。
