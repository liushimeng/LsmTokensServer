# 对话分析页面状态筛选 List 控件与查询优化方案

> 日期：2026-10-14　　阶段：CV（v2.0.78）　　状态：已实施（合并提交）
> 影响页面：`/ChatAnalysis`（管理员 Web 9101 与 用户 Web 29001 共用同一组件，一次修改两端生效）
> 涉及层次：前端 `ClientWeb/src/pages/chat-analysis/` + 后端 `ServerGo/models/subtable.go`
> 关联提交：`aa42d13`（阶段CV：对话分析状态筛选升级——可编辑 List 控件（34 个 HTTP 状态码，含 429/529/404）+ 查询修复）

## 1. 背景与问题分析

### 1.1 现状梳理

`对话分析` 页面筛选工具栏中 `状态` 条件当前是一个自由文本输入框（`ChatAnalysisToolbar.jsx`），
旁边已有 `取反` 勾选框；后端 `QueryAgentHttpTransactions`（`ServerGo/models/subtable.go`）按
`filter_status` 做 SQL：

```go
if filterStatus != "" {
    if filterStatusNot {
        query = query.Where("response_status != ?", filterStatus)
    } else {
        query = query.Where("response_status = ?", filterStatus)
    }
}
```

### 1.2 发现的核心缺陷（查询优化点）

**`response_status` 列存储的是 `http.Response.Status` 完整文本，不是纯数字状态码。**

写入路径：`proxy/server_http_ai_proxy.go:334` `responseStatus := resp.Status` →
`SaveAgentHttpTransaction`（`models/subtable.go`）原样入库。生产库实际数据抽样：

| response_status 实际值 | 说明 |
|---|---|
| `200 OK` | 标准格式「码 + 空格 + 短语」 |
| `404 Not Found` | 同上 |
| `529 `（尾随空格） | Anthropic 限流专用码，Go `http.Status` 无对应短语 |

因此 **现有 `WHERE response_status = '200'` 精确匹配永远命中 0 行**（除非上游恰好写入裸
"200"），`状态` 筛选与 `取反` 实际上是失效功能。本次需求"相关的数据查询必须支持"的实质，
就是把匹配语义修正为**状态码前缀匹配**。

### 1.3 需求清单

1. `状态` 查询条件改为「List 控件选择 + 可编辑」组合框：只能输入数字，列表项为 34 个
   标准 HTTP 状态码（含 429、529、404）；
2. `取反` 勾选功能全链路支持（List 选择值 / 手输值 × 取反 都要能查出数据）；
3. 全部查询条件（含状态、取反）localStorage 持久化，刷新页面后保持记忆；
4. 管理端与用户端两个 Web 同步生效。

## 2. 解决方案设计

### 2.1 前端：可编辑状态码 List 控件（datalist 组合框）

技术选型：原生 `<input list>` + `<datalist>`（工程内 `DstEndPointManage.jsx` 已有同模式先例，
零依赖、双端构建无差异）。控件行为：

- 输入框获得焦点 / 输入时下拉展示候选状态码（码值 + 语义短语辅助识别）；
- 点选候选项 → 输入框填入纯数字码（如 `429`）；
- 手动输入 → `onChange` 即时过滤：剔除全部非数字字符、最长 3 位（`\D` 剔除 + `slice(0,3)`）；
  粘贴 "429 Too Many Requests" 也会被净化为 "429"；
- `inputMode="numeric"`：移动端弹数字键盘；
- `取反` 勾选框保留在紧邻位置，语义 = `response_status NOT LIKE '码%'`。

状态码候选清单（共 34 项，标准 RFC 9110 + Anthropic 扩展 529，必含 429/529/404），
落地于 `statusOptions.js` 的 `HTTP_STATUS_OPTIONS`（`code` 为纯数字码、`label` 为语义短语）：

| 分类 | 状态码（码 + 短语） |
|---|---|
| 1xx 信息 | 100 Continue、101 Switching Protocols |
| 2xx 成功 | 200 OK、201 Created、202 Accepted、204 No Content、206 Partial Content |
| 3xx 重定向 | 301 Moved Permanently、302 Found、304 Not Modified、307 Temporary Redirect、308 Permanent Redirect |
| 4xx 客户端 | 400 Bad Request、401 Unauthorized、402 Payment Required、403 Forbidden、404 Not Found、405 Method Not Allowed、408 Request Timeout、409 Conflict、413 Payload Too Large、415 Unsupported Media Type、422 Unprocessable Entity、429 Too Many Requests、451 Unavailable For Legal Reasons |
| 5xx 服务端 | 500 Internal Server Error、501 Not Implemented、502 Bad Gateway、503 Service Unavailable、504 Gateway Timeout、505 HTTP Version Not Supported、507 Insufficient Storage、511 Network Authentication Required、**529 Overloaded (Anthropic)** |

清单与净化函数落在独立无依赖模块 `chat-analysis/statusOptions.js`（node 自检脚本
可直接加载），`constants.js` re-export 保持既有 import 路径不变；组件渲染在
`ChatAnalysisToolbar.jsx`。净化语义：前端 `sanitizeStatusCodeInput` 全局剔除非数字
（输入交互习惯，粘贴 "429 Too Many Requests" → "429"）；后端
`NormalizeStatusCodeFilter` 取前导数字（接口直调兜底）；两者在所有真实输入形态上收敛一致。

### 2.2 前端：localStorage 记忆

`useChatAnalysisFilters.js`（v2.0.7x 阶段CS 已实现）已按角色隔离 key
（`lsm:chat_analysis:filters:manager|user`）debounce 300ms 保存全部筛选，其中已含
`filterStatus` / `filterStatusNot`。本次仅需在**恢复路径**补一道同样的数字净化
（防止历史遗留脏值如 "200 OK" 直接回填输入框），不需要改存储结构。

### 2.3 后端：状态码前缀匹配（查询修正）

`models/subtable.go` `QueryAgentHttpTransactions` 中两处（count 查询 + 列表查询）同步修改：

```go
if code := NormalizeStatusCodeFilter(filterStatus); code != "" {
    pattern := code + "%"
    if filterStatusNot {
        query = query.Where("response_status NOT LIKE ?", pattern)
    } else {
        query = query.Where("response_status LIKE ?", pattern)
    }
}
```

新增导出函数 `NormalizeStatusCodeFilter(s string) string`（与既有
`ParseResponseStatusCode` 同域放置）：

- TrimSpace 后截取**前导连续数字**（至多 3 位），其余（空格、短语、非数字）全部丢弃；
- 无有效数字返回 ""（即不生效该筛选，天然兼容旧客户端传空/脏值）；
- 匹配语义变为前缀匹配：
  - `200` → `LIKE '200%'` 命中 `200 OK`；
  - `529` → `LIKE '529%'` 命中 `529 `（尾随空格）；
  - 手输 1~2 位亦按前缀生效：`5` → 全部 5xx（顺手获得的档位式筛选能力）；
  - `取反` → `NOT LIKE '码%'`；
- LIKE 前缀模式可走 `response_status` 既有索引（gorm `size:50;index`）的前缀范围扫描，
  相比全表 `%xxx%` 无性能回退。

管理端（`server_api_manager_chat_analysis.go`）与用户端
（`server_api_user_chat_analysis.go`）handler 均透传 `filter_status` /
`filter_status_not` 给 `QueryAgentHttpTransactions`，**单一修改点双端自动生效**，接口
协议不变（字段名、类型均不动），旧前端发来的请求也兼容。

### 2.4 i18n

`chatAnalysis.statusPlaceholder` 三语更新为提示可输码/选码的文案（zh：`如 200`，
en：`e.g. 200`，ja：`例: 200`）。`chatAnalysis.invert`（取反）已存在，不动。

## 5. 风险与兼容性

- **协议零变更**：请求/响应字段不变，仅语义从「全串精确匹配」改为「状态码前缀匹配」；
  旧语义本来就查不到数据，无行为回退风险；
- **历史 localStorage 脏值**：恢复路径净化兜底；
- **索引利用**：`LIKE '200%'` 前缀匹配可走索引；`NOT LIKE` 为过滤条件，与其他筛选叠加
  时由 MySQL 优化器合并索引选择，实际由 `user_name+model_name` 分表定位主导，无回退；
- **双端构建**：改动均在共用组件与共享常量内，`__APP_ROLE__` 门控不受影响，
  `dist-user` 不含任何管理端字样（本次未触碰管理端专属代码）。
