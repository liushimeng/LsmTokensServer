## 三、数据源研读：`TAgentHttpTransactionDataItem`

表定义：`ServerGo/models/mysql_http_agent_model.go:102`（分表 `TAgentHttpTransactionDataItem_%02d`，
共 `config.G.DBMysqlSubTableNumber` 张，按 `user_name`+`model_name` 哈希分片）。

### 3.1 时间字段语义（**本阶段最关键的研读结论**）

| 字段 | 注释语义 | 落库实况 | 可用性 |
|---|---|---|---|
| `created_at` | 记录创建时间 | ≈ `request_start_at` + 响应耗时 + 落库延迟 | ⚠️ **不可用于时段分析**（长请求会被拖后，峰谷失真） |
| `request_start_at` | 代理服务收到请求的开始时间戳 | 真实用户发起调用的时刻 | ✅ **唯一可信的「用户使用时间」轴** |
| `request_end_at` | 代理服务发送请求到目标服务的时间戳 | **恒等于 `request_start_at`** | ❌ 不可用 |
| `response_start_at` | 收到目标服务响应第一个字节的时间戳 | **恒等于 `request_start_at`** | ❌ 不可用（TTFB 恒为 0） |
| `response_end_at` | 收到完整响应的时间戳 | 真实 | ⚠️ 仅供参考（≈ `created_at`） |
| `elapsed_ms` | 总耗时(TTLT)，毫秒 | 真实 | ✅ 唯一的端到端时延度量 |

**结论 1（时间轴）**：高峰/低谷分析必须以 `request_start_at` 为准。
现有实现 `qosBucketTs()`（`mysql_http_agent_qos_stats.go:347`）已遵循此规则
（`request_start_at` 非零且不晚于 `created_at` 时优先），本阶段保持不变，并在文档中固化该约定。

**结论 2（TTFB 不可用）**：`ServerGo/proxy/server_http_ai_proxy.go:422` 落库时传入
`requestStartAt, requestStartAt, requestStartAt, responseEndAt` —— 代理路径**没有采集真实首字节时间**，
`request_end_at` / `response_start_at` 均为 `request_start_at` 的副本。
因此 `GetTokensRangeStats`（`mysql_http_agent_tokens.go:206`）里的 TTFB/Gen 计算对代理流量恒为空，
本方案**不引入** TTFB / 流式生成耗时指标（避免展示恒 0 的假指标）。

**结论 3（排队拥堵只能由「归一化系数」刻画）**：无法直接测得「上游排队秒数」，
只能用**输出 Token 归一化的拥堵系数**（`elapsed_ms ÷ (分档基准 ms/Token × 输出 Token)`）反推：
系数 ≈ 1 表示无排队，显著 > 1 表示该时段该源站存在排队/降速。本阶段沿用并强化该口径。

### 3.2 统计字段（服务质量口径所需）

| 字段 | 用途 | 本方案使用方式 |
|---|---|---|
| `dst_model_name` | 源站模型名 | 聚合主键（空值行跳过：无源站归属的直连失败） |
| `dst_endpoint_id` | 源站接入点 | 备用（区分同模型多接入点），本阶段不拆分 |
| `response_status` | 响应状态文本 | 分类：2xx 成功 / 429 限流 / 5xx 故障 / 其他 |
| `elapsed_ms` | TTLT | 时延口径（`ok_*` 成功口径） |
| `tokens_output_size` | 输出 Token | 归一化分母（10 档对数分箱） |
| `tokens_input_size` / `tokens_all_size` | 输入 / 总 Token | 备用（暂不入 QoS 口径） |
| `user_name` | 用户名 | 用户端数据隔离（JWT claims 强制过滤） |
| `created_at` / `request_start_at` | 见 §3.1 | 桶时间轴 |

  —— 源站→接入点映射，本阶段暂不接入（聚合维度已是 `dst_model_name`）。

### 4.4 算法

**（1）小时画像 `buildQoSHourProfile(m, base, now)`**

复用 `m.hours`（近 7 天 × 24 = ≤168 个小时桶，**无二次扫描**）：
按 `t.Hour()` 把 7 天的小时桶归并到 24 个时段桶 → `mergeQoSBuckets` → 一次
`finalizeQoSBucket`（与小时桶/天桶/窗口统计完全同一套口径）。
- `Calls` = 该时段 7 天总调用；`AvgCallsPerDay` = `Calls / 7`；
- `AvgCongestion` = 样本加权均值（`finalizeQoSBucket` 天然给出）；
- `OkP95Ms` = 该时段 7 天全部成功请求的 P95（跨天分位，代表「该时段的典型 P95」）；
- `Confidence` = 复用 `qosForecastConfidence(coefficient_samples)`。

**（2）时段带 `buildQoSTimeBands(hourProfile, days)`**

把 24 个小时按 `qosTimeBands` 归并：
- `Calls` = Σ 小时调用；`AvgCallsPerDay` = `Calls / days`；
- `AvgCongestion` = Σ(小时系数 × 小时样本) / Σ 小时样本（样本加权）；
- `ErrorRate` = Σ(小时错误率 × 小时调用) / Σ 小时调用（调用加权）；
- `Share` = `Calls / 总调用 × 100`；
- `Confidence` = 该带内样本数分档。

`Bands24h` 用「近 24 小时」的 24 个小时桶按带归并（每带覆盖 4/3/3/2/4/6 小时不等，
注意**各带时长不同**，`Share` 必须除以带内**总**调用而非固定长度）；
`Bands7d` 用 7 天小时画像归并。

> ⚠️ 口径提示：各时段带时长不同（凌晨 6h、午间 2h…），**横向比较必须看 `AvgCallsPerDay`
> 或 `Share`，不能直接比 `Calls`**。前端在时段带图上以「日均调用」为主轴。

**（3）峰谷 `buildQoSPeakValley(hourProfile, bands, todayRemaining, now)`**

- `PeakHour` = `AvgCallsPerDay` 最大的有样本小时；`ValleyHour` = 最小（**只在 `Calls>0` 的小时中取**，
  否则「凌晨没流量」会被误判为谷底）；
- `ForecastPeakHour` = 今日剩余时段（`now.Hour()+1 … 23`）中，预测系数最大且 `samples>0` 的小时；
- `TomorrowPeakBandKey` = 7 天口径中拥堵系数最高且样本达标的时段带；
- `TopBands` = 按 `Share` 降序的时段带列表。

**（4）全站汇总 `aggregateQoSReport(...)`**

全站口径**不做原始耗时求和**（各源站基准不同，混算无意义），改为**指标级再聚合**：
- 调用量 / 错误数 = 求和；
- 拥堵系数 = Σ(模型系数 × 模型样本) / Σ 模型样本（跨模型样本加权）；
- 错误率 = Σ(模型错误数) / Σ 调用数；
- P95 = 取各模型 P95 的**最大值**（保守：全站最差体验），并在 UI 标注为「最差模型 P95」。

### 4.5 API 层（`ServerGo/api/server_api_qos_monitor.go`）

- 解析请求体 `{"refresh": true}` → **绕过 30s 缓存**（手动刷新必须拿到新快照）；
  默认走缓存（保护服务端，避免高频全表扫描）。
- 缓存 TTL 由 30s **延长到 60s**（无自动刷新后缓存命中率更高、服务端压力更小；
  手动刷新走 `refresh=true` 旁路）。

### 5.6 `QoSPeriodTable.jsx` —— 逐时段明细（**无下拉**，需求 2）

拆成两个子视图：

1. **「时段 × 模型」矩阵**（`QoSPeriodMatrix.jsx`）：
   - 行 = 时段（24h 窗口 → 24 行小时桶；7d 窗口 → 7 行天桶）；
   - 列 = 源站模型；
   - 单元格 = 可切换指标（拥堵系数 / 调用量 / 错误率 / 成功平均时延）；
   - 着色规则：系数/错误率用四档状态色；调用量用单色（分类色槽 1）+ 数值，
     不用「值越大越深」的 ramp（antipattern：值 ramp 应用于有序连续量，调用量是量级不是序数等级；
     此处用**单色 + 数值**，避免双重编码）。
2. **全模型逐时段长表**（`QoSPeriodTable.jsx` 重写）：
   行 = 模型 × 时段（长表），列 = 模型 / 时段 / 请求数 / 成功 / 成功均值 / 成功 P95 /
   ms/Token / 拥堵系数 / 卡顿率 / 抖动率 / 429 / 5xx / 其他 / 错误率（沿用既有列集 + 模型列）；
   默认按「模型 → 时段倒序」排序；低样本显示 `—`。
