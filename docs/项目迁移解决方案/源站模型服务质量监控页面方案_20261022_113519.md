## 一、背景与目标

运维需要实时掌握「各个模型源站」的**服务质量（QoS）**：网络时延、排队拥堵、错误限流。
现有页面（ModelInfo / ChatAnalysisTotal）只展示调用量与 Tokens 规模，缺少**质量维度**。

本方案新增「服务质量监控」页面，核心思路是**Token 归一化 + 分位统计**：
以「基准推理速度（ms/Token）」为标尺，把不同大小的请求折算成可横向对比的
「拥堵系数」，再按时间桶聚合出卡顿率 / 网络抖动率 / 限流与错误率，用
状态卡 + 折线 + 热力图 + 堆叠柱状图直观呈现。

## 二、数据源与表结构依据

数据源：交易分表 `TAgentHttpTransactionDataItem_00 ~ _07`（8 张，按
`(user_name, model_name)` 哈希分表）。本方案涉及字段：

| 字段 | QoS 含义 |
|---|---|
| `created_at` | 记录落库时间（请求完成后） |
| `request_start_at` | 代理收到请求的时间戳（**时间桶首选**，兜底 `created_at`） |
| `dst_model_name` | 目标源站模型 → **聚合维度（"模型源站"）** |
| `elapsed_ms` | 总耗时 TTLT（毫秒）→ 时延 / 拥堵系数分子 |
| `tokens_output_size` | 输出 Tokens → 拥堵系数分母 |
| `response_status` | 完整状态文本（"200 OK"/"529 "）→ 经 `ParseResponseStatusCode` 解析：2xx 成功 / 429 限流 / 5xx 服务故障 / 其他错误 |
| `user_name` | 用户端（29001）数据隔离键 |

SELECT 仅小字段（`id, created_at, request_start_at, dst_model_name, response_status,
tokens_output_size, elapsed_ms, user_name`），严格避开 8 个 longtext（v2.0.42 白名单契约）。

## 三、核心计算逻辑

### 3.1 基准推理速度（ms/Token）
对每个 `dst_model_name`，取近 7 天**成功请求（2xx 且 `tokens_output>0` 且 `elapsed>0`）**：

```
baseline = Σ elapsed_ms / Σ tokens_output   （ms/Token）
```

作为该模型无排队时的推理耗时基准。随查询滚动窗口自动重算（等效「每日凌晨
自动更新」，且更灵敏——厂商模型版本升级当天即可反映），服务端缓存 60s。

### 3.2 拥堵系数（排队强度）
单请求：`coefficient = elapsed_ms / (baseline × tokens_output)`（`tokens_output=0`
或基准缺失的请求不参与拥堵统计）。分档：

| 档位 | 区间 | 卡片色 |
|---|---|---|
| 正常 ok | < 1.2 | 绿 `#0ca30c` |
| 轻度 light | 1.2 ~ 2.0 | 黄 `#fab219` |
| 中度 moderate | 2.0 ~ 5.0 | 橙 `#ec835a` |
| 严重 severe | > 5.0 | 红 `#d03b3b` |

单请求系数上限截断 100（防脏数据拉爆均值）。消除 Token 大小影响，可跨请求、
跨时段横向对比。

### 3.3 其余指标（均按时间桶计算）
- **卡顿率** stall_rate：桶内 `coefficient > 2.0` 的请求数 / 桶内参与拥堵统计的请求数
- **网络抖动率** jitter：桶内 `elapsed_ms` 标准差 / 平均值（变异系数）
- **429 率 / 5xx 率**：桶内对应状态请求数 / 桶内总请求数
- **时延**：桶内 `elapsed_ms` 均值与 P95（桶内存原始值，Go 端排序取分位）

### 3.4 时间维度聚合
一次扫描统一覆盖**最近 7 天**，Go 端双粒度分桶：

| 视图 | 桶粒度 | 桶数 | 用途 |
|---|---|---|---|
| 实时窗口 | 最近 5 分钟滚动 | — | 状态卡「实时拥堵系数 / 当前平均时延 / 错误率」（分钟桶切片） |
| 1 小时视图 | 1 分钟 | 60 | 折线图「近 1 小时」 |
| 天维度 | 1 小时 | 24 | 折线图「近 24 小时」+ 错误堆叠柱 |
| 周维度 | 1 天 | 7 | 折线图「近 7 天」+ 周级 P50/P95 长期健康基准 |
| 拥堵热力图 | 7 天 × 24 小时 | 168 | 单模型定位每日高峰拥堵时段 |

> 与原设计的差异（工程取舍）：原设计「每秒刷新的 1 分钟滑动窗口」需要常驻
> 后台采样任务；本方案改为**服务端 60s 缓存 + 前端 30s 自动刷新**，分钟级新鲜度
> 已满足排队/限流观测（429/拥堵的演化周期远大于分钟级），且零新增后台任务。
> 原设计「1 分钟指标存 7 天 / 小时存 30 天 / 天存 1 年」的物化存储表同样省略：
> 交易表默认保留 45 天（`transactionRetentionDays`），7 天窗口内**一次扫描原始行
> 即可现算全部桶**（7 天数据量 ≈ 全量 1/6，keyset 分页内存有界），无预聚合表
> 也无一致性维护成本；如未来保留期 < 8 天或模型数暴涨，再引入物化表不迟。

## 四、后端实现

### 4.1 新增文件 `ServerGo/models/mysql_http_agent_qos_stats.go`

- `QoSBucketPoint`：单桶聚合结果（`bucket` 键、`count`、`avg_elapsed_ms`、
  `p95_elapsed_ms`、`avg_congestion`、`stall_rate`、`jitter`、`err429/err5xx/errOther`
  计数与率、`tokens_out`）。
- `QoSModelReport`：单模型报告（`dst_model_name`、`baseline_ms_per_token`、
  `baseline_samples`、`live{...}`、`minutes[60]`、`hours[24]`、`days[7]`、
  `heatmap{days[7][24]}`、`week_p50_ms`、`week_p95_ms`、`status`、`alert`）。
- `QoSMonitorReport`：全部模型报告 + `generated_at_ms` + 顶部汇总。
- `GetQoSMonitorReport(userName string, subTableNum int) (*QoSMonitorReport, error)`：
  - 遍历 8 张分表，keyset 分页（复用 v2.0.58 模式，本文件独立行结构
    `qosScanRow`），`created_at >= now-7d` 预过滤；`userName != ""` 时追加
    `user_name = ?`（用户端隔离）。
  - 扫描过程中按 `(dst_model, 分钟桶)` 与 `(dst_model, 小时桶)` 增量累积：
    elapsed 列表、系数列表、状态分类计数、tokens 汇总；同时累计 7 天基准分子分母。
  - 扫描结束后统一算率 / 分位 / 抖动 / 状态卡，分钟桶切片出 live 窗口（最近 5 分钟），
  小时桶切片出 24 小时与 7×24 热力图，小时桶聚合出 7 天桶与周 P50/P95。
  - 结果以 `(userName, subTableNum)` 为键缓存 60s（包内独立小缓存，
    不与 5 分钟 statsCache 混用，保证实时视图新鲜度）。
  - NilDB / ctx 取消安全：返回空报告而非 panic；分表缺失跳过。

### 4.2 新增文件 `ServerGo/api/server_api_qos_monitor.go`

- `qosMonitorInterfaceHandle`（管理端）：POST `/QoSMonitorInterface`，全站维度，
  返回 `userManageResp{Success, Data: QoSMonitorReport}`。
- `userQoSMonitorInterfaceHandle`（用户端）：`getUserToken(r)` 取 claims，
  `UserName` 强制取 JWT claims（防越权），数据仅覆盖本人请求命中的源站模型。

### 4.3 路由注册 `ServerGo/api/routes.go`
- `RegisterManagerAPIRoutes`：`/QoSMonitorInterface`（自动受 ManagerAuthMiddleware 保护）。
- `RegisterUserAPIRoutes`：`/QoSMonitorInterface` → 用户版 handler。

## 五、前端实现

### 5.1 菜单统一（用户端复制管理端结构）
`ClientWeb/src/shared/navConfig.js` 用户树由「路由与模型」单组改为与管理端一致的
五组结构（仅少管理端专属 UserManage）：

```
总览 🏠        → 首页
用户与路由 👥   → 源站管理 / 路由管理
模型与代理 🧠   → 模型信息 / Agent信息 / 协议分析器 / 服务质量监控★
对话分析 💬     → （不变）
爬虫与数据 🕷   → （不变）
```

管理端与用户端均在 `model-proxy` 组新增 `ServiceQuality`（`nav.serviceQuality`）。
`nav.routeModel` 键随之废弃（三语言 locale 同步删除）。

### 5.2 页面 `ClientWeb/src/pages/service-quality/`

模块化拆分（对齐 chat-analysis 范式）：

| 文件 | 职责 |
|---|---|
| `index.jsx` | 页面骨架：单次拉取 `QoSMonitorInterface` → 分发数据；30s 自动刷新（可关）；窗口切换（1h/24h/7d） |
| `QoSCards.jsx` | 模型状态总览卡：状态点（四档色）+ 实时拥堵系数 + 当前平均时延 + 错误率；告警（系数>2 或错误率>5%）卡片高亮描边；点击选中模型联动热力图 |
| `QoSTrendChart.jsx` | 时延趋势折线：X 时间 / Y 平均响应时长(ms)，多模型分色折线 + 同色虚线 P95；图例点击选模型；1h/24h/7d 切换；crosshair + tooltip |
| `QoSHeatmap.jsx` | 拥堵热力图：7 天(行) × 24 小时(列)，单元格颜色 = 桶均拥堵系数四档色 + 无数据灰；悬浮 tooltip 显示系数/请求数/时延 |
| `QoSErrorBars.jsx` | 错误堆叠柱状图：按时间桶堆叠 429 / 5xx / 其他错误计数；段间 2px 留缝；tooltip |
| `index.jsx` 底部 | DataTable 全模型明细表（时延/系数/卡顿率/错误率/基准），兼作低对比色系的表格视图出口 |

配色（经 palette 校验器验证）：
- 多模型分类色固定顺序 8 槽（`#2a78d6 #eb6834 #1baf7a #eda100 #e87ba4 #008300 #6250d6 #e34948`），
  超出折叠「其他」；图例 + tooltip + 明细表保证低对比槽位的可辨识。
- 状态四档色仅用于状态语义（卡片/热力图），始终伴随文字标签，不与系列色混用。
- 折线 2px、网格极细实线、图例常驻；tooltip 十字线对齐。
